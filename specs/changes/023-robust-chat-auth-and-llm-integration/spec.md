# 023-robust-chat-auth-and-llm-integration: Устойчивый диалог, Guardrails, Cookie-аутентификация и чистые профили

## Цель
Устранить дефекты пользовательского сценария:
1. Обеспечить корректную обработку немедицинских запросов (Out-of-Domain Guardrails) и вопросов по выбранным препаратам из аптечки без сбоя UI и без исключений JavaScript.
2. Синхронизировать клиентский слой аутентификации с Cookie-based сессиями бэкенда (`HttpOnly` куки `medai_session`), сохранять сессию при обновлении страницы и подключить эндпоинт пользователей к панели администратора.
3. Обеспечить чистый стартовый профиль (пустая аптечка и пустая медкарта) для всех новых пользователей и гостей.
4. Внедрить системный клинический промпт MedAI и возможность генерации ответов через LLM-интеграцию (OpenAI-compatible / Ollama / DeepSeek) со структурным fallback-режимом.

## Допущения и контекст
- Бэкенд на FastAPI использует безопасную авторизацию на базе JWT в `HttpOnly Cookie` (`medai_session`).
- В `frontend/src/api/client.js` обращения к API должны идти по относительному пути `/api/v1` с `credentials: 'include'`.
- Дизайн-система и верстка Каты неприкосновенны; доработки касаются логики рендеринга и скриптов в `frontend/`.

## Требования
- **REQ-001 (Out-of-Domain Guardrail):** Реализовать классификатор домена `medai/dialogs/guardrails.py`. Запросы вне медицинской сферы («как готовить блины», «напиши код на питоне» и др.) не направляются в BM25, а возвращают статус `out_of_domain` с вежливым клиническим дисклеймером («Я медицинский ассистент MedAI...»).
- **REQ-002 (Kit Context Enrichment):** Если в диалоге передаются выбранные препараты из аптечки (`selected_pills` или вопрос вида «что это»), система использует метаданные и инструкцию к препарату для генерации исчерпывающего клинического описания.
- **REQ-003 (LLM & Assistant Synthesis):** В `medai/dialogs/service.py` и `medai/llm/` реализовать адаптер к OpenAI-compatible LLM (с использованием системного промпта MedAI, RAG-контекста, противопоказаний и дозировок). При отсутствии ключа — детерминированный структурированный генератор без сбоев.
- **REQ-004 (Admin Users API):** Реализовать эндпоинт `GET /api/v1/admin/users` с проверкой роли `role IN ('admin', 'superadmin')`, возвращающий реальный список пользователей из PostgreSQL.
- **REQ-005 (Frontend Resilient Chat):** В `frontend/src/components/Chat.js` устранить обращение к незащищенным полям `rec.medicine_name`. Поддерживать как карточки RAG, так и текстовые сообщения ассистента. В блоке `finally` гарантировать разблокировку кнопки отправки и возврат маскота в состояние `idle`.
- **REQ-006 (Cookie Auth & Session Restore):** В `frontend/src/api/client.js` использовать относительный путь `/api/v1` и `credentials: 'include'`. В `frontend/src/api/auth.api.js` и `login.html` убрать зависимость от `res.token` в теле JSON; при старте приложения восстанавливать профиль через `GET /api/v1/auth/me`.
- **REQ-007 (Empty Default State):** В `frontend/src/api/kit.api.js` и `frontend/src/state/store.js` удалить предустановленные моковые списки (`DEFAULT_KIT` и дефолтные аллергии). Новые пользователи и гости начинают с пустой аптечки (`[]`) и пустой медкарты.
- **REQ-008 (Admin Table Integration):** В `frontend/admin.html` загружать список пользователей динамически через API `/api/v1/admin/users` вместо статического мок-массива.

## Сценарии взаимодействия (BDD)

### Сценарий 1: Обработка немедицинского запроса без зависания интерфейса
- **Given** открыт чат ассистента
- **When** пользователь отправляет сообщение *"Как готовить блины?"*
- **Then** ассистент вежливо сообщает, что специализируется исключительно на доврачебной помощи и препаратах аптечки; маскот возвращается в состояние `idle`, поле ввода и кнопка разблокированы.

### Сценарий 2: Вопрос о препарате из аптечки
- **Given** пользователь прикрепил в чате препарат из аптечки *"Парацетамол"* и ввел *"что это"*
- **When** запрос обрабатывается системой
- **Then** возвращается информация о препарате (фармгруппа, показания, способ применения и предостережения), кнопка и чат продолжают работать без ошибок `TypeError`.

### Сценарий 3: Регистрация нового пользователя и сохранение сессии
- **Given** неавторизованный пользователь регистрируется через форму `login.html`
- **When** регистрация завершена и страница перезагружена (F5)
- **Then** сессия восстанавливается по `medai_session` cookie через `GET /api/v1/auth/me`, аптечка и медкарта пользователя пустые, а в панели администратора отображается новый зарегистрированный аккаунт.
